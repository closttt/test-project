Ты аудируешь сайт так, как это делалось на лендинге менторства в сентябре
2026 (см. `docs/perf-*.md` и историю CLAUDE.md проекта). Принцип один:
**сначала измерь, потом называй проблему.** Каждая находка в отчёте
подтверждена числом из замера или строкой кода, у каждой есть решение и
оценка эффекта.

## 0. Подготовка

1. Прочитай CLAUDE.md проекта: там ограничения заказчика (что нельзя сжимать,
   что должно остаться живым, а не видео, и т. п.). Не предлагай то, что уже
   отвергнуто.
2. `npm run build` (прод-сборка обязательна, dev ничего не показывает),
   `npm run start -p 3100` в фоне. Dev-сервер на 3000 при замерах гасить:
   он роняет TBT на 50–70 мс.
3. Инструменты: `npx lighthouse@12`, Playwright из `node_modules`
   (`NODE_PATH=node_modules`), `CHROME_PATH` на chromium из
   `%LOCALAPPDATA%/ms-playwright`. Пробы лежат в `scripts/perf/`:
   - `probe-load.cjs` — что грузится на старте (JS/CSS/шрифты/внешние хосты),
     длинные задачи, число раскладок, WebGL-контексты, кадры по секциям;
   - `probe-gpu-mobile.cjs` — draw-calls по канвасам на разных позициях
     скролла (что рисует, пока его не видно) и мобильный вьюпорт 390px;
   - `probe-cpu-profile.cjs` — профиль ЦП первых 12 с под ×4: какой скрипт
     и какая функция жгут поток по секундам;
   - `shots.cjs` — скриншоты секций, лайтбокса, меню, логина и кабинета
     для сравнения «до / после»;
   - `lh-summary.cjs` — выжимка из JSON Lighthouse (LCP, TBT, длинные задачи,
     forced reflow, неиспользуемый JS).

## 1. Замеры (обязательные, все)

```bash
npx lighthouse@12 http://localhost:3100/ --preset=desktop --throttling.cpuSlowdownMultiplier=4 --output=json --output-path=lh-desktop.json --chrome-flags="--headless=new" --quiet
npx lighthouse@12 http://localhost:3100/ --output=json --output-path=lh-mobile.json --chrome-flags="--headless=new" --quiet
node scripts/perf/lh-summary.cjs .
NODE_PATH=node_modules node scripts/perf/probe-load.cjs
NODE_PATH=node_modules CPU=4 node scripts/perf/probe-load.cjs
NODE_PATH=node_modules node scripts/perf/probe-gpu-mobile.cjs
NODE_PATH=node_modules CPU=4 node scripts/perf/probe-cpu-profile.cjs
```

Замедление ×4 обязательно: PageSpeed заказчика считает на железе вчетверо
слабее рабочей машины, обычный `--preset=desktop` почти ничего не показывает.
Заголовок `Style & Layout` в разбивке главного потока больше `Script` — это
принудительные пересчёты раскладки, ищи их в `forced-reflow-insight` и профиле
(`getComputedStyle` в GSAP, чтение `offsetHeight` в кадре анимации).

## 2. Чек-лист — что смотреть в коде и в замерах

**Загрузка.** Стартовый JS по файлам (fingerprint чанков: three, motion,
lucide, sonner, base-ui — что реально нужно первому экрану?). Лениво ли
грузятся тяжёлые библиотеки, и не стартует ли «ленивая» сборка по таймеру у
всех посетителей. HTML: размер, инлайн-CSS, дубли CSS во flight-данных
(`self.__next_f`), общая ли таблица стилей с другими разделами сайта.
Внешние хосты: `preconnect`, старт загрузки не после прелоадера. Шрифты:
число файлов, `font-display`, лишние подсеты (символ ₽ тянет latin-ext).

**Гидратация.** Самая длинная задача и что в ней: `gsap.set` при
монтировании на десятках элементов, `ScrollTrigger.refresh` с пинами,
синхронный `setState` в эффектах. Стартовые состояния анимаций должны
приезжать из CSS, а не ставиться из JS.

**Анимации.** Каждый цикл кадра: сколько rAF-петель, что рисуется за экраном
и под другими секциями (sticky-хиро под наездом). Чтения раскладки в
`onUpdate`/scrub (`offsetWidth`, `getBoundingClientRect`, `getComputedStyle`)
— кэшировать на `refreshInit`. Длительности и кривые сверять с исходником,
не «нормализовать». `prefers-reduced-motion` у каждой анимации.

**WebGL.** Число живых контекстов (потолок Chrome 16, iOS меньше и теряет
молча) — один рендерер на группу сцен. Разрешение рендер-таргетов против
того, что реально видно (квантование в ячейки — таргет по сетке ячеек, не
по пикселям). Компиляция шейдеров — `compileAsync`, не первым кадром.

**Видео.** Вес, битрейт, размер кадра против размера окна на экране,
`preload`, `+faststart`, автоплей за экраном, рендеры под мобильные,
кодек (AV1 с H.264-фолбэком). Проверка качества — VMAF, не глаз. Пережим
H.264 «в тот же размер» обычно даёт файл больше исходника. Сжатием
занимается агент `video-converter`.

**Картинки и иконки.** Формат (webp/avif; PNG только там, где нужен —
OG-картинка, favicon), `sizes` против реального размера показа, `priority`
только у LCP-кандидата, неиспользуемые файлы в `public/`, preload лишних
картинок в `<head>`. SVG-иконки инлайном или одним файлом, не десятком
`<img>`.

**Мобильный вьюпорт.** 390×844 dpr 3: горизонтальный скролл, элементы за
кромкой, что грузится (те же 1540px-ролики?), число канвасов, root font-size.

**Гигиена.** `tsc`, `eslint`, консоль без ошибок и предупреждений, зависимости
не в том разделе, мёртвые компоненты (Toaster без единого `toast()`),
dev-инструменты в прод-бандле, неиспользуемые ассеты.

## 3. Отчёт

Формат: таблица метрик, затем проблемы по приоритету (что не так → чем
подтверждено → решение → ожидаемый эффект), затем план с порядком работ.
Разделяй «критично / средне / мелочи». Без эмодзи и общих слов вроде
«оптимизировать»: у каждого пункта конкретный файл и конкретная правка.

Что делать **не надо**: предлагать выкинуть анимации ради баллов (заказчик
их заказывал), сжимать hero-видео без показа, менять дизайн, тащить
UI-библиотеки, «модернизировать» рабочий код без замера.

## 4. После правок

Пересобери, повтори все замеры из п. 1 и `shots.cjs`, сравни скриншоты
попиксельно (Playwright) или глазами через Read, сведи таблицу «до / после /
Δ %». Если какая-то метрика не улучшилась — так и напиши, с причиной.
Проверь, что параллельные правки других сессий не потеряны (`git status`,
`git diff --stat`).
