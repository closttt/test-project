# Клиентский конвейер — оркестратор

Твоя задача: пользователь не помнит порядок этапов и не запускает агентов
руками. Он говорит «продолжай» — ты определяешь состояние проекта и двигаешь
конвейер до следующей точки, где без пользователя не обойтись.

## Вызовы

| Команда | Что делает |
|---|---|
| `/client-pipeline` | статус проекта → продолжить конвейер с нужного места |
| `/client-pipeline new <Название-проекта>` | создать папку клиента в `own-projects/` → сразу этап брифа |
| `/client-pipeline status [проект]` | только показать состояние, ничего не запускать |
| `/client-pipeline feedback <текст или файл>` | цикл правок: feedback-decoder → design-review |

## Структура папок — ЗАКОН

Все клиентские проекты живут в **`own-projects/`** в корне репозитория.
Один клиент — одна папка `own-projects/<Название-проекта>/`, внутри всегда:

| Папка | Что внутри |
|---|---|
| `documents-from-clients/` | все документы **от клиента**: логотип, бренд-гайд, тексты, прайсы, фото, доступы, переписка, выгрузка старого сайта |
| `research/` | наша аналитика: `brief.md`, `research.md`, `ia.md`, `feedback/` |
| `audits/` | наши аудиты и выгрузки: `competitors-audit.md`, скрины `competitors/<конкурент>/`, ревью макетов `reviews/` |
| `our-documents/` | документы клиенту от нас: КП, `estimate.md`, `tech-work.md` |

Плюс `status.md` в корне папки проекта — журнал этапов.

Все четыре папки создаются **сразу при создании проекта, даже пустые**, —
чтобы ни одному агенту не пришлось выдумывать, куда писать. Артефакты — только
внутри папки проекта, в корне репозитория ничего не создавать.

## Определение проекта

0. Текущая папка сама является проектом (в корне есть `status.md` или папки
   `documents-from-clients/`, `research/`, `our-documents/`) → это проект,
   корень папки = корень проекта (так живут коммерческие проекты вне
   Mentorship, например `Commercial Projects/<Имя>/`).
1. Аргумент — путь или имя → ищи папку `own-projects/<имя>/`.
2. Без аргумента: текущая папка лежит внутри `own-projects/<имя>/` → это проект.
3. Кандидатов несколько → один вопрос через AskUserQuestion со списком папок
   из `own-projects/`.

Дальше везде работай с **абсолютным путём проекта** и передавай его каждому
агенту в промпте: «Проект: `<путь>`. Все чтения и записи — только внутри этого
пути, по структуре папок проекта». Без этого агент, запущенный из корня
репозитория, пишет артефакты не туда.

## Карта этапов

Порядок жёсткий; готовность этапа определяется его артефактом.
Пути артефактов — относительно папки проекта.

| # | Этап | Агент (subagent_type) | Артефакт-маркер | Режим | Нужно от пользователя |
|---|---|---|---|---|---|
| 1 | Бриф | `brief-expander` | `research/brief.md` | **интерактивный** | ответы на раунды вопросов |
| 2 | Ресёрч | `researcher` | `research/research.md` | фоновый | — |
| 3а | Аудит конкурентов | `researcher-audit-figma` | `audits/competitors-audit.md` | фоновый | ссылка на Figma-файл |
| 3б | ИА | `ia-architect` | `research/ia.md` + FigJam | фоновый | ссылка на FigJam-файл проекта |
| 4 | Смета | `price-client` | `our-documents/estimate.md` | фоновый | — |
| 4б | КП в Figma | `kp-content` | `our-documents/kp.md` | фоновый | ссылка на КП-темплейт в Figma |
| 5 | ТЗ | `tech-work` | `our-documents/tech-work.md` | фоновый | Notion-страница (или найдёт поиском) |
| 6 | Прототип | `create-prototype` | строка в `status.md` + Figma-ссылка | фоновый | Figma-файл (или создаст новый) |

Этапы **3а и 3б независимы** — после ресёрча запускай оба параллельно,
одним сообщением с двумя вызовами Agent. Этап **4б не блокирует конвейер**:
как только `estimate.md` готов и ссылка на темплейт есть — запускай
`kp-content` параллельно с ТЗ; ссылки нет — этап «ждёт», конвейер идёт дальше.
В промпт `kp-content` передай путь проекта и ссылку на темплейт дословно.

Цикл правок вне очереди, в любой момент: `feedback-decoder`
(артефакты `research/feedback/*.md`) → `design-review`
(артефакты `audits/reviews/*.md`).

## Алгоритм

1. **Состояние.** Проверь артефакты-маркеры файлами (Glob) и прочитай
   `status.md` проекта. Файлы сильнее status.md: артефакт есть, а строки
   нет → допиши строку сам.
2. **Статус-табличка** пользователю: этап → готов/следующий/ждёт → дата.
3. **Входы одним заходом.** Посмотри, какие внешние входы понадобятся на
   ближайших этапах (Figma-ссылка для аудита, ссылка на КП-темплейт для
   `kp-content`, Notion для ТЗ, Figma для прототипа), и спроси **все
   недостающие одним вопросом** — не дёргай
   пользователя на каждом шаге. «Нет пока» — нормальный ответ: этап с
   недостающим входом помечается «ждёт», конвейер идёт по тем, что могут работать.
4. **Запуск следующего этапа:**
   - **бриф** — интерактивный: прочитай `.claude/agents/brief-expander.md`
     и выполняй его инструкции прямо в основном чате (сабагент не умеет
     вести раунды вопросов с пользователем);
   - остальные — через Agent tool по имени из карты. В промпт агенту: путь
     проекта, собранные входы (ссылки), и что от него ждём.
5. **После каждого этапа:** убедись, что артефакт появился в нужной папке
   и в `status.md` есть строка; покажи пользователю 3–5 строк сути (не пересказ
   документа); **автоматически переходи к следующему этапу**.
6. **Остановка** — только в трёх случаях: конвейер дошёл до конца; следующий
   этап ждёт ввод пользователя; агент вернул блокер или вопрос — покажи его
   дословно, не отвечай за пользователя.
7. **Финал конвейера:** сводка — все артефакты со ссылками (Notion, Figma),
   и один общий список «Открытые вопросы» — собери секции открытых
   вопросов/допущений из brief, tech-work, estimate и feedback без дублей.

## Notion — каждый документ сразу туда

После каждого этапа документ выгружается в Notion через `mcp__notion__*`:
«Проекты с клиентами» (id `3ac76a26-89f7-8069-80c5-e22fbe0d15e5`) →
страница клиента (emoji) → подстраницы:

| Подстраница | Из файла |
|---|---|
| Бриф + дочерняя «Анкета по темплейту» | `research/brief.md`, `research/brief-questionnaire.md` |
| Ресерч | `research/research.md` |
| ИА — структура сайта | `research/ia.md` + ссылка на карту сайта и user flow в FigJam-файле проекта |
| Смета — без обоснования; допущения, «не входит», «оплачивает отдельно» — полно | `our-documents/estimate.md` |
| ТЗ + дочерняя «Структура сайта по блокам» (или «Контент») | `our-documents/tech-work.md`, `content-structure.md` (выгружает сам `tech-work`) |

**КП в Notion не создаём** — КП живёт только в Figma. Выгрузку больших
документов можно отдавать сабагенту. Формат: таблицы
`<table header-row="true">`, склейка абзацев, неразрывный пробел после «+»;
replace_content на странице с дочерними — без allow_deleting_content и с
сохранением `<page url=…>` в конце. После заливки — retrieve и проверка.

## Ресёрч — живой файл

`research/research.md` — глобальный документ, из которого собирается ТЗ.
Первая версия — после брифа. После ИА и после аудита конкурентов в Figma
(`researcher-audit-figma`) — перезапусти `researcher` на доработку, затем
`tech-work` на обновление ТЗ и «Структуры сайта по блокам». Пока аудита нет,
ТЗ и структура блоков — заготовка (пометка в шапке).

## Правки пользователя → агенты

Каждая правка пользователя по формату, объёму или подходу документа — это
правка агента, а не только документа: обнови `.claude/agents/<агент>.md`
(и этот SKILL.md, если правка про процесс) и **сразу скопируй изменённые
файлы в Mentorship** — `Desktop/Claude/My works/Mentorship/.claude/agents/`
и `.claude/skills/client-pipeline/`. Затем переделай документ уже по
обновлённому агенту.

## Режим `new <Название-проекта>`

1. Создай каркас целиком:
   - `own-projects/<Название-проекта>/documents-from-clients/`
   - `own-projects/<Название-проекта>/research/`
   - `own-projects/<Название-проекта>/audits/`
   - `own-projects/<Название-проекта>/our-documents/`
   Все папки создаются сразу, пустые — это нормально.
2. В `documents-from-clients/README.md` — список, что клиенту положить
   (логотип, бренд-гайд, прайсы, тексты, фото, доступы).
3. В корне проекта `status.md` — шапка: имя проекта, дата старта.
4. Папка с таким именем уже существует → не пересоздавать и ничего не
   затирать: покажи её состояние и продолжи конвейер с нужного места.
5. Сразу этап 1 — бриф в основном чате.

## Режим `feedback`

1. Запусти `feedback-decoder` сабагентом, передав текст/файл фидбека и путь проекта.
2. Покажи четыре списка из результата.
3. Если у пользователя есть макет на руках (ссылка на ноду Figma, скрин,
   URL) — предложи сразу `design-review` против свежего фидбека; после правок
   по фидбеку design-review обязателен перед отправкой клиенту.

## Правила

- **Не перепрыгивать этапы.** Нет `research/brief.md` → любой запрос
  («посчитай смету») начинается с брифа; объясни одной строкой и веди по порядку.
- **Не перезапускать готовое** без явной просьбы («пересчитай смету»,
  «обнови ресёрч»). При перезапуске старый артефакт не удалять —
  переименовать в `<имя>-old-<дата>.md`.
- Пользователь просит конкретный этап — запусти его, но покажи, если
  пропущены предыдущие.
- Артефакты — только в папках проекта по структуре выше; ни в корне
  репозитория, ни в корне `own-projects/` ничего не создавать.
- Агент упал или MCP недоступен → зафиксируй этап как «ждёт» с причиной
  в status.md и продолжи те этапы, что не зависят от упавшего.
